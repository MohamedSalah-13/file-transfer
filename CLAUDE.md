# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

LAN file-transfer + chat app ("WhatsApp for files"): one JavaFX **server** app and any number of JavaFX **client** apps talking over raw TCP sockets. Java 21, JavaFX 21, AtlantaFX themes, Ikonli icons (Feather pack), Maven (wrapper included). Docs and comments are partly in Arabic; `docs/1.md`–`docs/15.md` are the step-by-step design notes the code was built from.

## Commands

Windows (PowerShell); use `./mvnw` on Unix shells.

```powershell
.\mvnw.cmd compile                 # build
.\mvnw.cmd -Pserver javafx:run     # run server (GUI, listens on port 5000)
.\mvnw.cmd -Pserver javafx:run "-Djavafx.args=--port 5050 --storage D:\ft-data"   # other port / storage
.\mvnw.cmd -Pclient javafx:run     # run a client (start several in separate terminals)
.\mvnw.cmd test                    # run all tests
.\mvnw.cmd test -Dtest=FileTransferServerTest   # one test class
.\docs\images\screenshots.ps1    # retake the README screenshots (AR + EN) from the real app; needs port 5000 free
.\packaging\package.ps1          # Windows installer -> target\installer (needs WiX 3.x; -Type app-image needs nothing)
```

- `packaging/package.ps1`: `javafx:jlink` makes the runtime image in `target/app` (it keeps `bin/keytool.exe`, which jpackage's own jlink step would strip), then `jpackage --runtime-image` makes the installer. The main launcher "File Transfer" is the client; `packaging/server-launcher.properties` adds "File Transfer Server" with `-Dfiletransfer.packaged=true`, which makes `ServerConfig.workDir()` use `~/.file-transfer/server` instead of the (unwritable, replaced on upgrade) install folder. Keep `--win-upgrade-uuid` unchanged so new versions upgrade in place.
- Icons: `packaging/IconMaker.java` draws them in code (a chat bubble with send/receive arrows; the server's adds a server badge). After changing it, run `java packaging/IconMaker.java` from the project root: it rewrites `packaging/client.ico`, `packaging/server.ico` (used by `package.ps1`) and `src/main/resources/icons/(client|server)-N.png` (the window icons set in `ClientApp` / `ServerApp`; dialogs inherit them from their owner).
- Updates: `client.Updates` builds the `AppUpdater` of the shared [desktop-updater](https://github.com/MohamedSalah-13/desktop-updater) library (JitPack, module `com.hamza.updater`); `ClientApp` and `ServerApp` each start an `UpdatePrompt` on their window. An installed copy looks at this repository's GitHub releases (8 s after the start, then every 6 h), offers a newer one in the window's language, downloads the asset matching `*-setup.exe`, checks its SHA-256, and runs it after the program closes. The running version comes from the jpackage launcher (`jpackage.app-version`), so a copy run from the IDE is never offered one; run with `-Djpackage.app-version=0.0.1` to see the offer. The client and the server share one installation, so the library asks to close the other one before installing. A release must not be a draft or pre-release and must carry the installer under a name ending in `-setup.exe`. A release that bumps `Protocol.VERSION` locks out clients that update before their server does: say so in the release notes, which the offer shows. Such a release can be published as required (`release.ps1 -Required`, or `<!-- update: required -->` in its description): older copies then get no "Skip this version". "Later" stays on purpose - `enforceRequired` is not used, because a client forced ahead of its server could no longer reach it. When a login fails with `version_mismatch` and the server's protocol is the newer one (`Updates.serverIsNewer`), the client looks for its update at once (`UpdatePrompt.checkQuietly`). The Appearance tab has the "Check for updates" button (`updates`, `check_updates`, `updates_version`, `updates_dev` keys). Fixes to update behaviour go into the library, not here.

- The `server` / `client` Maven profiles only switch `mainClass` (`server.ServerLauncher` / `client.ClientLauncher`). Without a profile `javafx:run` starts the server.
- Tests (JUnit 5, Surefire 3.x) live in `src/test/java` in the same packages as the code, so Surefire patches them into the JPMS module and they can use package-private members.
  - `SafeNamesTest`, `AccountStoreTest`, `KnownServersTest`, `LastLoginTest`, `AppearanceTest`, `PanelLayoutTest`, `NotifySettingTest`, `LocalFilesTest`, `FileLauncherTest`, `SearchTextTest`, `ServerAppTest`: plain unit tests.
  - `FileTransferServerTest`: starts a real TLS server on a free port in a `@TempDir` and speaks the raw wire protocol, so a protocol change must update its `Wire` helper too. Creating the test certificate runs `keytool` once per class.
  - `ClientConnectionTest`: runs `ClientConnection` against a scripted fake server (deterministic stalls and cut-offs). It starts the JavaFX toolkit (`Platform.startup`), so it needs a desktop session, not a headless CI box.
- Runtime data goes to `server-storage/` in the working directory (git-ignored), unless `--storage` or `server.properties` says otherwise.

## Architecture

Packages under `src/main/java/com/hamza/filetransfer/`:
- `shared/`: wire constants (`Protocol`), limits (`Limits`: 200 MB max file, 64 KB buffer), `SafeNames` (validation/sanitizing for anything that becomes a path), and `Discovery` (LAN discovery datagrams).
- **LAN discovery (UDP `Discovery.PORT` = 5001):** `client.ServerFinder` broadcasts a query (to 255.255.255.255, each interface's broadcast address and 127.0.0.1) and `server.DiscoveryResponder` (started by `ServerApp`, optional) answers with its protocol version, TCP port and host name. The responder uses `SO_REUSEADDR` so several servers on one machine can all answer, and never sends a reply larger than the query (no amplification). `ServerFinder.merge` folds the answers a server sends from each of its networks into one row, shown as 127.0.0.1 when the server is on this computer. An answer is only a hint: TLS pinning still decides trust.
- `server/`: `FileTransferServer` (socket logic, no JavaFX UI code), `AccountStore` (passwords), `ServerApp` (table of `TransferSession`s). `ServerApp` reuses the client's UI helpers (`client.I18n`, `client.ThemeManager`, `client.Appearance`): all its text has `server_*` / `column_*` / `transfer_status.*` keys, and its language and theme are kept in `~/.file-transfer/server-ui.properties`, apart from the client's. Paths and English messages inside its Arabic text are wrapped in U+202A...U+202C (`ServerApp.leftToRight`); JavaFX honors that embedding (LRM does not fix a leading `--`). The server updates a `TransferSession` from socket threads; `ServerApp` calls `deliverUpdatesOn(Platform::runLater)` so its properties change only on the FX thread (progress updates are coalesced).
- `client/`: `ClientConnection` (socket logic + callbacks) and `ClientApp` (the client UI, built in code — no FXML). The top bar holds only the status, Connect/Disconnect, the two panel toggles and ⚙ Settings. `SettingsWindow` is an owned stage with a Connection tab (host, port, find, user, password, connect; it opens at start and closes after a successful login, and trust/find dialogs are owned by it) and an Appearance tab (language, theme). `SidePanels` puts users | chat | transfers in a `SplitPane`: dividers resize the side panels, hiding removes a panel and showing puts it back at its remembered width (divider positions account for half a divider), and only the chat grows with the window. `PanelLayout` saves the widths and visibility to `client.properties` when the window closes. Button icons come from Ikonli's Feather pack through `client.Icons` (`Icons.on(button, Feather.X)`); they are font glyphs, so AtlantaFX colors them like the button text in every theme. Don't put emoji in button text. File bubbles carry Download, or Open and Show in folder when the file is on this computer: `LocalFiles` (`~/.file-transfer/local-files.properties`, message id -> path) remembers downloads and sent originals (`sendFile` returns the message id from `SEND_OK`), and thread loads restore `localPath` from it. `FileLauncher` opens with `Desktop.open` and shows with `explorer.exe /select, <path>` (two arguments: as one, a path with spaces opens Documents instead), always off the FX thread; `FileLauncher.canRunPrograms` makes Open on a received program or script ask first, with Cancel as the default. `ClientApp.openFile` / `showInFolder` / `downloadInto` are seams for tests. Chat search (`ClientApp.chatSearch`, Ctrl+F) matches through `SearchText.normalize` (case, accents, tashkeel and tatweel ignored; أإآٱ→ا, ى→ي, ة→ه, ؤ→و, ئ→ي) on message text or file name, keeps the matching ids, and restyles bubbles (`bubble-search-match` / `-current`); it re-runs when `chatMessages` changes, staying on the same message. Scrolling to a match uses `ListView.scrollTo` and then `VirtualFlow.scrollTo` on the next pulse, because variable-height bubbles make the first jump stop short near the end. The module `requires org.kordamp.ikonli.javafx` and `org.kordamp.ikonli.feather` (the pack registers itself as an `IkonHandler` service), and both land in the jlink runtime. Files dragged from Explorer onto the chat (`ClientApp.acceptDroppedFiles`, a `StackPane` around the chat with a `.drop-overlay` label) are sent with `ClientApp.sendFile`, the same path as the Send File button (which sends every file in `ClientApp.attachments`, picked with `showOpenMultipleDialog`, then clears it; tests fill that list directly since the native dialog can't be driven); file drags are handled in event filters so the message field never pastes their paths, and folders are skipped. Unread counts: a message is read only if it lands in the open chat while the window is focused (`windowInFront`); focusing the window marks the open chat read, and the total shows as "(n)" in the window title. When the window isn't focused, `notifyNewMessage` shows a Windows notification through `DesktopNotifier` (an AWT `TrayIcon`, hence `requires java.desktop`; all AWT calls on its own thread, the icon is added on first use and removed in `ClientApp.stop()` so the JVM can exit), at most one per sender per 4 s, with only the sender and "New message" or the file name (the push carries no text). `NotifySetting` (`notifications=` in `client.properties`) switches it off. `ClientApp.notifier` and `windowInFront` are package-private seams for tests.

### Wire protocol
- **TLS 1.3 on every socket** (CONTROL and TRANSFER; settings in `shared.Tls`). Since 2.0.0 there is no plain-TCP mode, so 1.x clients and servers can't connect.
  - **Server:** `ServerTls.loadOrCreate` makes a self-signed EC certificate with the JDK's `keytool` on first start and keeps it in `server-storage/tls/` (`server.p12` + password file). `ServerApp` shows its SHA-256 fingerprint. Deleting that folder creates a new identity, and every client will then refuse to connect until its user re-trusts it.
  - **Client, trust on first use:** `TofuTrustManager` accepts only the fingerprint trusted for `host:port` in `KnownServers` (`~/.file-transfer/known_servers.properties`). An unknown server fails with `untrusted_server` (arg: fingerprint) before the password is sent; `ClientApp` shows the fingerprint, saves it if the user trusts it, and reconnects. A changed fingerprint fails with `server_cert_changed` (args: new, trusted, file) and is blocked; `ClientApp.askToTrustChanged` shows both fingerprints, keeps "Close" as the default button, and enables "Trust the new certificate" only after the user ticks that they compared it with the server window. Every retry re-checks the certificate against the one just saved. A server without TLS gives `tls_failed`.
- **Framing:** `DataInputStream`/`DataOutputStream` with `writeUTF` commands followed by positional fields. There is no length envelope, so **client and server must read and write exactly the same fields in the same order**. Any protocol change means editing `Protocol`, the server handler, and the `ClientConnection` reader together, **and bumping `Protocol.VERSION`**.
- **Version check:** every socket starts with `CONNECT <Protocol.VERSION:int>` (1 for the 2.x apps, 2 since 3.0, which added deleting messages), followed right away by `HELLO`/`HELLO_TRANSFER` (no reply in between). On a mismatch the server answers `AUTH_FAILED version_mismatch <serverVersion> <clientVersion>` and closes. A bare `HELLO` (a client from before versioning) counts as version 0. A server from before versioning answers `CONNECT` with `ERROR bad_handshake`, which `ClientConnection.loginError` reports as `version_mismatch 0 <ours>`. Never change the `CONNECT` format itself; it is how any two versions recognize each other. The comments in `Protocol.java` document the handshake.
- **Two kinds of socket per user:**
  - **CONTROL:** `HELLO user password` → `HELLO_OK canonicalName token`. One CONTROL socket per user (`online` map): a new successful login replaces and closes the old one, so a client that vanished without closing can't lock its user out (the server no longer sends `HELLO_TAKEN`). It carries listing commands, text messages (`SEND_TEXT`), and server pushes (`INCOMING_FILE`, `INCOMING_TEXT`).
  - **TRANSFER:** `HELLO_TRANSFER user token`. One extra socket per file transfer: `SEND_FILE` (reply `SEND_OK`/`ERROR` on that socket) or `DOWNLOAD`, then the client closes it (`ClientConnection.openTransfer`). So uploads never block chat, and several transfers run in parallel. The token is only valid while the issuing CONTROL socket is online. **Cancelling** a transfer (the ✕ in the transfers panel, `SimpleTransferRow.cancel` -> `TransferHandle.cancel`) closes that TRANSFER socket; there is no protocol message for it. `TransferSocket.abort` closes the raw TCP socket under the TLS layer, because `SSLSocket.close()` from another thread waits for the write lock a stalled upload holds and would freeze the FX thread. The client reports `TransferCancelledException` (row status `CANCELLED`); the server sees a dropped upload, deletes the half `.bin`, writes no `.meta`, pushes nothing, and shows `INTERRUPTED`. The ✕ hides once an upload has sent every byte, since the server may already have delivered it. The server still accepts `SEND_FILE` on CONTROL, for 1.0.0 clients.
- **Write locking:** every write to a socket's output goes inside `synchronized (lock)`. The server pushes notifications to *other* users' CONTROL streams through `FileTransferServer.push`, which runs on the recipient's own `pusher` thread (`OnlineClient`), so a slow or dead recipient never blocks or disconnects the sender.
- **Responses are async on the client:** `ClientConnection.listenLoop` dispatches each server message to a callback via `Platform.runLater`. `SEND_OK` is ignored, and after sending, the UI simply re-requests the thread (`requestThread`) to refresh. `THREAD_MESSAGES` echoes the peer; the UI only shows it if that peer is still the open chat.
- **Client threading:** never touch the socket from the FX thread. The constructor (connect + login) runs on a background thread; `requestThread`/`requestUsers`/`requestMyFiles` are queued on the `client-requests` thread. Set callbacks before calling `ClientConnection.start()`.
- **Deleting messages (protocol 2, app 3.0):** `DELETE_MESSAGE <peer> <messageId> <ME|EVERYONE>` on CONTROL -> `DELETE_OK <messageId>` | `ERROR` (`message_not_found`, `not_your_message`, `bad_delete_scope`, `delete_incomplete`). ME removes only the caller's `.meta` (and a received file's inbox copy). EVERYONE is only for the sender's own OUT message: both copies are replaced by a `messageType=DELETED` placeholder that keeps just id, direction, users and time (the text or file name is gone), the recipient's inbox `.meta`/`.bin` are deleted, and the recipient gets `MESSAGE_DELETED <messageId> <fromUser>`. `THREAD_MESSAGES` entries of type `DELETED` carry no more fields. Deletes run under one server-wide lock. Delete for everyone changes the recipient's side first (their placeholder, their inbox file) and the sender's copy last, and every step skips what is already done (placeholders keep `deletedType` TEXT/FILE): if a step fails it answers `delete_incomplete` with the sender's message untouched, so the user can simply retry, and a repeat is a harmless `DELETE_OK`. The client asks with `ClientApp.askToDelete` (right-click > Delete..., or the Delete key; Cancel is the default) and re-requests the thread right after; a `MESSAGE_DELETED` push re-requests that peer's thread.
- **Users can't message themselves:** the client hides its own name and the server rejects it (`self_recipient`); otherwise the IN and OUT `.meta` copies would be the same file.
- **Errors are codes, not text:** `ERROR` / `AUTH_FAILED` carry `<code> <argCount> <args...>` (codes in `shared.ErrorCode`; client-only codes in `client.AppError`). The client shows them through `I18n.error(...)`, so a new code needs an `error.<code>` entry in all three `messages*.properties`. English values with `{0}` args go through `MessageFormat`, so avoid apostrophes in them.

### Server storage layout (`server-storage/`)
```
accounts.properties                         # key = lowercase username; value = iterations:salt:hash:displayName (PBKDF2)
keys/storage.key                            # AES-256 master key for everything under users/ (losing it loses all stored data)
users/<user>/inbox/<messageId>.bin|.meta    # received file bytes + metadata (download source)
users/<user>/threads/<peer>/<messageId>.meta  # chat history, one Properties file per message
```
- **Encrypted at rest (`StorageCrypto`, since 2.7.0):** every `.bin` and `.meta` under `users/` is in the "FTE1" format: `"FTE1" | 16-byte salt | segments`. Per-file key = HMAC-SHA256(master, label || salt); the plaintext is cut into 64 KiB segments, each AES-256-GCM with nonce = segment number and AAD = header || context || segment number || last flag. So downloads stream (no whole-file buffering), each segment is verified before it is sent, truncation/reordering fails, and the context — the file's path under `users/`, lower-cased (`FileTransferServer.context`) — makes a file copied into another place fail to decrypt. The download size is `StorageCrypto.plainSize(Files.size(bin))`. Always read and write stored files through `crypto`; never `Files.newInputStream` on a `.bin` or `Properties.load` on a raw `.meta`. Folder names, message ids and file sizes (roughly) stay visible.
- **Migration:** `FileTransferServer.startAsync` encrypts any plain `.bin`/`.meta` left from 2.6.0 and older (temp file + atomic move; files that already start with `FTE1` are skipped, leftover `*.encrypting.tmp` deleted), so it is cheap on later starts. The key protects copies/backups of `users/`, not someone who can read all of `server-storage/`.
- Each message is written twice: once IN for the recipient and once OUT for the sender. Only the IN copy is `downloadable=true`. A message deleted for everyone keeps both `.meta` files as `messageType=DELETED` placeholders, encrypted like any `.meta` and moved over the old one atomically (`replaceWithPlaceholder`).
- `.meta` files are `java.util.Properties`, always written with `Properties.store` (never string concatenation) so values can't inject keys, then encrypted.
- There is no database; listing a thread reads every `.meta` file in the folder and sorts by `timestampMillis`.

### Security invariants (keep these when changing code)
- Every username, peer, file id, or file name from the network goes through `SafeNames` before touching the file system.
- Build paths with `SafeNames.resolveInside(base, child)`, never a raw `Path.resolve`.
- Usernames are NFC-normalized and case-insensitive. After login, always use the canonical name returned by `AccountStore.authenticate`.
- The client sanitizes received file names and never overwrites an existing file when saving into a folder (`ClientConnection.uniqueTarget`).
- All traffic is TLS 1.3. Clients pin the server certificate by fingerprint (trust on first use), so the first connection is only safe if the user compares the fingerprint with the server window. Never add a trust-all fallback.
- Nothing under `users/` is written or read in plain text: use `StorageCrypto` with the file's `context`. Never overwrite or regenerate an existing `keys/storage.key`.

### Known issues
- `messages*.properties` must stay UTF-8: Java 9+ reads resource bundles as UTF-8. The Arabic file was once saved with a non-UTF-8 encoding, which turned every character into `?`. Client UI text goes through `client.I18n` (`I18n.bind(key)` for live bindings that follow language switches); add new strings to all three `messages*.properties` files.
- Server port and storage come from `ServerConfig.load`: `--port`/`--storage` args, then `server.properties` in the working directory (git-ignored), then 5000 / `server-storage`. `FileTransferServer.startAsync` binds before returning, so a busy port throws `BindException` and `ServerApp` shows it. The client fills host, port and user from `LastLogin` (`~/.file-transfer/client.properties`, saved after each successful login with the canonical name, never the password); a missing or broken file gives the defaults in `LastLogin.DEFAULT` (127.0.0.1:5000, user1). The same file keeps the picked language and theme (`Appearance`, saved when a picker changes). Both go through `PrefsFile.update`, which re-reads the file and replaces only its own keys, so neither save drops the other.
- The server certificate is created with `keytool` from `java.home/bin`. A jpackage/jlink runtime built with `--strip-native-commands` (jpackage's default) has no `keytool`; `package.ps1` avoids that by building the runtime with `javafx:jlink` and checks that `keytool.exe` is there.
